# Reliability audit — 2026-09-09

A full audit of the orchestrator after a period in which fleet runs kept
stalling, tasks failed for reasons nobody could see, and every interrupted run
left wreckage that made the next one worse.

Twelve defects, all fixed. They are documented here because most of them are
*coupled* — the same run reproduces several at once, and fixing one in
isolation moves the failure rather than removing it. Where a fix changed a
documented behaviour, the governing doc was updated too; this file is the
record of **why**.

Commits: `6cbcb17`, `d5504cf`, `92f3fb1`, `7d06e66`, `219c672`, `3323e15`,
`8cfc32a`, `7a98129`, `2300e6e`.

---

## 1. Review diffs were taken against a moving ref

**`gitstore.diff_full` compared the worktree against the live `main`.**

Merges are serialized but tasks run in parallel, so `main` advances while a
task is still working. Every file a sibling merged after this task's `alloc`
therefore appeared in the review diff as a **deletion by this task**:

```
diff --git a/mathx.py b/mathx.py
deleted file mode 100644
```

…in a task that never touched `mathx.py`. Reviewers rejected the scope
violation — correctly, given what they were shown — and the task burned a fix
round every time, then its escalations, on work that was already right.

This made parallelism self-defeating: the more tasks ran at once, the more
often correct work was rejected and escalated to a scarcer model for nothing.

**Fix:** diff against the merge base of the task branch and the base ref.

**Measured**, identical two-task run, same models:

| | before | after |
| --- | --- | --- |
| implement attempts | 8 | 2 |
| reviews | 8 (7 rejections) | 2 (0 rejections) |
| escalations | 2 (gpt-oss → DeepSeek → GLM → Kimi) | 0 |
| outcome | 1 merged, 1 failed | both merged |
| wall clock | >10 min (timed out) | ~2 min |

Regression test: `tests/test_gitstore.py::ReviewDiff`.

## 2. Resume escalated infrastructure failures

`start_model` escalated **any** row at `failed`, including rows the stale-reset
wrote because the owning process was *killed*. Being interrupted says nothing
about whether a model was strong enough.

Observed live at 16:40:43–45: one killed queue resumed four task files, and
`escalated_on_resume` pushed all of them to **Kimi-K3** — the scarcest tier
(driver cap 2) and the most stall-prone. Result: `inflight.over_cap kimi=9/3`,
then `provider.api_error: 400` on every request.

**Fix:** escalate only on a recorded *capability* failure
(`code_tasks._is_capability_failure`). Infrastructure reasons resume at the
same tier.

Related: `escalated_on_resume` compared against the **task file's** original
routing rather than where the task last ran, so every resume of an
already-escalated task was reported as a fresh escalation. It is the number an
operator reads to decide whether the fleet is about to pile onto a scarce
model, so it now measures against the previous run.

## 3. Drivers leaked both concurrency slots

`Driver.run` released the in-process semaphore and the cross-process DB lease
only on success and on `DriverError`. Any other exception — a missing harness
binary, a bug inside `_once`, cancellation during shutdown — leaked a
semaphore permit **for the life of the process** and left a lease row pinning
the model at its cap until the TTL expired.

**Fix:** `_guarded_once` holds both slots in nested `try/finally`.

---

## 4. Capacity rejections were retried on the crash schedule

A harness rejected at the ARC account cap never got a slot. Retrying it 2 s
later walks straight back into the same cap and deepens the pile-up.

**Fix:** classify capacity rejections (`Driver.is_capacity_error`) and back off
on a long jittered ladder (`ARC_DRIVER_CAPACITY_BACKOFF`, 45 s → 300 s).

---

## 5. A stopped run could not clean up after itself

`SIGTERM`'s default action terminated the process outright, so the cleanup
block never ran: tasks stayed at `running`, leases were held until their TTL,
and cancellation never reached the drivers — their `kimi`/`opencode` children
survived, still holding ARC slots. **A killed run made the cap situation worse
rather than better.**

**Fix:** the run races the graph against a stop event; a signal cancels the
graph, which unwinds through the drivers (killing children) and then the run's
own cleanup. Verified end to end.

---

## 6. One node's crash cancelled every sibling

The graph set `done` on the first node error and cancelled all workers. In the
code workload a sibling is a whole task that may be minutes into an
implement/review it will successfully merge — cancelling threw that away and
orphaned its worktree, row and lease.

**Fix:** on failure the graph stops *scheduling* immediately but lets
in-flight nodes finish, bounded by `drain_timeout`. Separately, a gather node
whose sources can no longer arrive now fails loudly instead of hanging the
process forever.

---

## 7. `store.upsert_code_task` discarded escalations

`ON CONFLICT DO UPDATE` set only `status`, `branch`, `worktree`, `error` — not
`model` or `reviewer`. The `escalate` node re-upserts a task at a stronger
tier, and that was silently dropped, so the row (and therefore the next
resume's starting tier, and the dashboard) showed a model the task no longer
ran at. It also nulled `branch`/`worktree` when re-upserted without them,
erasing the allocation still in use.

**Fix:** update `model`/`reviewer`; `COALESCE` `branch`/`worktree`.

---

## 8. `run-queue.sh` did not serialize, and never reported failure

Two defects:

- `wait_free` polled `pgrep`, so every waiting instance saw the same process
  exit and started **simultaneously** — the direct cause of §2's four-way
  pile-up.
- `rc=$?` always read `0`, because the `$(date)` in the same `echo` ran first
  and reset `$?`. Every task file reported success.

**Fix:** a `flock`, and rc captured before any other command runs. The queue
also reconciles before its first task file.

---

## 9. The wall clock had become the binding limit on real work

Observed live: a Kimi-K3 implement was killed at exactly `DRIVER_TIMEOUT=900s`
having written 149 KB with only **80 s** of idle. It was demonstrably still
working, and each such kill costs a full retry (`MAX_RETRIES=4` — roughly an
hour per large task).

`DRIVER_IDLE_TIMEOUT` (300 s of silence) is the precise stall detector and is
proven in production; the wall clock only needs to catch a harness that
dribbles output forever without converging.

**Fix:** `DRIVER_TIMEOUT` → 2700 s.

That immediately broke `DRIVER_LEASE_TTL`'s own documented invariant — it was
pinned at 1800 s and must exceed `DRIVER_TIMEOUT` plus retry backoff, or a
lease is reaped while its driver still runs and another driver takes the slot,
putting the model over its cap. **The lease table's whole purpose, defeated by
a constant edit elsewhere.** It is now derived, and
`tests/test_config.py` encodes the coupling.

## 10. Dashboard: counting, caps, and invisible failures

- **Every agent counted twice.** The fleet spawns the kimi CLI, which writes
  its own kimi-code wire log, so a driver was counted from its `driver.start`
  event *and* from that log. Killed attempts compound it: each leaves an
  unanswered `llm.request` that reads as live for 10 minutes. With two kimi
  processes actually running, `/api/health` reported four agents. Sessions
  whose directory names a fleet worktree (`wd_<task-id>_<hash>`) are now
  excluded from in-flight — their token totals are still counted, since kimi's
  stream-json carries no usage.
- **Two different caps shown as one.** `driver_cap` is how many harness
  instances the *fleet* may run, deliberately below the ARC account cap so
  interactive use still has room; `account_cap` is ARC's limit, which fleet
  drivers and the operator's own kimi sessions both consume. Conflating them
  reported "Kimi-K3 4/2 OVER CAP" while the fleet correctly ran one driver.
- **A cancelled driver emitted no terminal event**, leaving a phantom agent
  against the cap for ~19 minutes until the stale sweep. Now
  `driver.cancelled`.
- **Failure reasons were invisible.** `code_tasks.error` has always been
  stored and was never rendered — a task went red with no way to learn why.
- **No stop control.** A run could be started from the UI but only killed from
  a shell.
- **No health surface.** The concurrency and stall facts existed only in
  `/api/usage`, a 32 KB payload the Projects page never fetched.
- `_projects` recomputed fix-loop stats (a full `harness_runs` read plus a
  full event-log walk) **once per task file** — 13× per 5-second refresh.
- Task titles, prompts, git output and event error text reached `innerHTML`
  unescaped; harness stderr contains angle brackets.
- `index.html` carried two navigation bars to the same three pages.

## 11. No tests, and gates that could not catch a break

There was **no test suite**. Task gates were greps — "does `drivers.py`
mention `driver.heartbeat`?" — which prove a string is present and nothing
more. Four queued task files assign agents to refactor `drivers.py`,
`dashboard.py`, `code_tasks.py`, `store.py`, `main.py` and
`static/index.html`; every one could have satisfied its gate while breaking
the engine, and the merge would have landed.

**Fix:** 96 tests (`tests/`, stdlib `unittest`) over graph execution and drain
semantics, taskfile validation, verdict parsing, resume/escalation planning,
driver slot accounting and backoff, lease caps, orphan reaping, dashboard
in-flight attribution, config invariants, and review-diff isolation between
parallel tasks — the last three against real temporary git repos.

`./check.sh` wraps compilation, imports, the tests, a JavaScript syntax check,
a DOM-reference check on every dashboard page, and validation of every task
file. **Every task file targeting this repo now starts its `verify_cmd` with
`./check.sh &&`**, and the planner prompt tells future plans to do the same.

One trap found while wiring this up: the tests emitted into the real
`logs/events.jsonl`, so — with `check.sh` in every gate — each gate run
injected fake `node_error`/`driver.error` records that the dashboard reported
to the operator as genuine fleet problems (942 had accumulated). Tests now
redirect `config.EVENTS_LOG` to a temp directory.

## New: `main.py code reconcile`

A run that died before it could clean up leaves stale `running` rows, driver
leases held by dead processes, and orphaned worktrees. `code reconcile` reaps
all three. It refuses to run while a `code run` is alive (`--force` to
override) and **never deletes a worktree holding uncommitted agent edits or a
branch with unmerged commits** — the orchestrator commits only at publish, so
an interrupted implement's entire output lives in its worktree as uncommitted
files. Counting commits alone would have called that "merged" and deleted it.

This is not hypothetical: the first production reconcile after these fixes
preserved 149 KB of interrupted Kimi work on exactly that rule.

See [runbook.md](runbook.md) § "Reaping orphans".

## 12. Nothing prevented two runs of one task file

Found while the fixes above were being verified: the queue was running
`dashboard-ui-recovery` while a run of `github-ops-and-heartbeat` had been
started from the dashboard's Run button — and that file was still in the
queue's own list, so the queue would have started a second run of it.

Driver leases kept the account inside its caps, which is what they are for,
but they cannot make two runs of *one* task file coherent: those share task
ids, worktrees and branches, and each performs a scoped stale-reset at startup
that would clobber the other's live rows.

Nothing prevented it from any direction. The dashboard checked only its own
launch registry, so a run started by the queue or a terminal was invisible to
it; `code run` checked nothing at all.

**Fix:** `code run` refuses when another process owns that task file (naming
the pid, `--force` to override); the dashboard consults live processes rather
than just its registry; the queue waits for a conflicting run to finish.
Different task files in parallel remain fine — that is the fleet.

## Follow-up: the stalls, diagnosed

The audit bounded the *cost* of a stall but left the cause inferred. Adding
instrumentation settled it on the first sample:

```
{'awaiting_api': True, 'model': 'Kimi-K3', 'waiting_s': 320.9}
```

At the moment of a stall the harness sits in state `S` burning no CPU, and its
kimi session log ends on an `llm.request` ARC had left unanswered for 320
seconds. It is **not** an agent loop and not a harness bug: the server accepted
the request and never replied. It reproduces on GLM-5.3 as well as Kimi-K3, so
it is not model-specific.

Consequences, all shipped:

- `DRIVER_IDLE_TIMEOUT` 300s → **120s**. Nothing arrives after the hang, so
  the remaining wait was pure cost.
- `driver.progress` heartbeats every 60s (bytes, idle time, `/proc` sample),
  so a live agent's progress is observable rather than inferred from transcript
  file size — and the stall event has a CPU baseline to diff against.
- Stall events carry `state`, `cpu_delta_s`, `blocked`, `last_activity` and the
  wire evidence, gathered before the kill because `/proc` dies with the process.
- A blocked stall is now **classified as a capacity error**, so it takes the
  long jittered backoff instead of the 2/4/8s crash ladder. It carries no HTTP
  400, but retrying it immediately walks back into the same saturation.
- The Fleet panel shows "quiet 90s · S · no CPU" on a live agent, and problem
  lines read "API never answered — Kimi-K3 outstanding 320s".

See [runbook.md](runbook.md) § "A harness stalled".

## Follow-up: the "stalls" were queueing, and we were killing healthy work

Tasks were dying mid-run once their conversation passed roughly 50-60k tokens.
Four hypotheses were tested directly against the API and **all four ruled
out** (Kimi-K3, fleet live):

| hypothesis | measurement |
| --- | --- |
| request size | 48k multi-turn returns in 9.4s |
| non-streaming | works, and *faster* than streaming (2.7s) |
| tool definitions / multi-turn shape | works, 9.4s |
| the ARC concurrency cap | rejects in **0.2s** with `400 {"detail": "concurrent session limit reached"}` |

That last one **disproves a claim this repo had been repeating**: ARC does not
"hold rejected/queued requests open instead of erroring" at its cap. It
rejects fast and cleanly.

### What was actually happening

The kimi wire logs carry per-step latency telemetry
(`llmFirstTokenLatencyMs`). Over 1927 completed steps:

- **median time-to-first-token is 1.0s at every context size** — it never moves;
- the **tail** grows with context: p90 goes 3.5s -> 16.4s, and the maximum
  reaches **308.9s**;
- those slow steps then stream their response normally in ~0.3s.

**They were healthy.** ARC queues under load rather than refusing, and
time-to-first-token is precisely what stdout silence measures — so the idle
timeout was killing requests that were about to succeed.

This inverts the change made earlier the same day. `DRIVER_IDLE_TIMEOUT` had
been lowered 300s -> 120s to "fail fast"; measured against the tail, that
raised the chance of destroying a healthy context-heavy task from 1.8% to
8.7% (p90 task, and a lower bound — a step we kill leaves no telemetry, so
the real tail is worse). It is now **420s**, which clears the observed tail.
`DRIVER_TIMEOUT` (2700s) still bounds the total.

The lesson worth keeping: **silence is not a hang**, and an instrument that
cannot tell "slow" from "dead" should be tuned to the slow case, because the
cost of the two mistakes is not symmetric — waiting 7 minutes for a dead
request is cheap, and killing a finished one is not.

### The two harnesses also differ on compaction

- **opencode's compaction works.** It fired twice inside one GLM-5.3 run,
  which then carried on to 621KB of output — against ~350KB left at the
  131072 default, where it never compacted at all.
- **kimi's compaction never completes.** 20 `full_compaction.begin` across the
  entire session history, **0** `full_compaction.end`, interactive sessions
  included.

So the context budget is per harness: opencode 65536 (compaction is a win),
kimi 131072 (firing a broken compaction earlier is strictly worse — tried,
measured, reverted the same day).

## Follow-up: what actually kills a task — terminated requests

The error was in kimi-code's **session log**, which nothing had been reading
(the wire log records the request but not its failure):

```
WARN llm request failed turnStep=0.12 model=arc/kimi-k3-fleet
     errorName=APIConnectionError errorMessage=terminated
```

ARC terminates long-running requests after roughly 310s in flight. Not a hard
ceiling — 27 responses succeeded past 300s of decode, one at 828.9s — but a
probability that climbs the longer a request stays open. kimi-code retries
them itself, at about five minutes a go.

**Response length dominates the failure rate:**

| workload | terminated |
| --- | --- |
| all sessions baseline | 179 / 2144 = 8.3% |
| the task prompted to rewrite a 504-line file | 6 / 18 = **33%** |

That task spent 30 of its 45-minute budget on retries and never finished. It
was progressing the whole time — 19 turn-steps — just paying a 33% tax.

So the taskfile was as much the problem as the infrastructure: a prompt that
says "rewrite ONLY static/index.html (currently 504 lines)" guarantees long
responses, which is exactly what gets terminated. `_impl_prompt` now tells the
implementer to make targeted edits even when the task sounds like a rewrite,
and explains why.

Also worth recording: kimi requests `maxTokens = 131072`, derived from
`max_context_size`. No separate output cap exists — `max_output_tokens`,
`max_tokens` and `output_tokens` were each set and observed to leave the
request unchanged. `kimi doctor` accepts unknown keys silently, so it cannot
be used to validate a guess.

## Follow-up: the agents were in plan mode

After all the timeout and context work, tasks were still "not doing work". The
transcript said why:

```
tools: {'Read': 11, 'Grep': 2, 'Bash': 3, 'Write': 1, 'ExitPlanMode': 1, 'Edit': 4}
"Now let me write the plan file with my findings and the execution approach."
```

`~/.kimi-code/config.toml` had `default_plan_mode = true`. Plan mode makes an
agent research and propose instead of editing, and leaving it requires
approving `ExitPlanMode` — which nothing does in a headless `kimi -p` run.

**182 of 206 sessions entered plan mode; 44 left it.** Most fleet agents ever
run on this box were researching and writing plan files, not code. A run would
burn its full budget, produce a 100KB transcript, and leave the worktree
completely clean — indistinguishable from a stall unless you looked at either
the tool calls or `git status` in the worktree.

Fixed by `default_plan_mode = false`, verified empirically rather than
assumed: the same headless prompt that previously planned now reads the file
and edits it, with `Read`/`Edit`/`Bash` and no `ExitPlanMode`.

`main.py code run` refuses to start while plan mode is on, and a test fails if
the box is reconfigured back — this is a global kimi setting the orchestrator
does not own, so it checks rather than assumes.

## Standing risks

- **ARC hangs requests at capacity, and no fix here changes that.** The
  instrumentation above proves where the time goes and the timeouts bound it
  (a stall costs ~2 min now, down from ~15), but a saturated account still
  means a task can exhaust its retries without ever getting an answer. This is
  upstream.
- **The ARC account is shared** between fleet drivers and interactive
  `kimi` sessions. The Fleet panel now shows both numbers; an interactive
  session genuinely competes with the fleet for the cap of 3.
- **Queued task files predate these repairs.** `dag-chaining`,
  `github-ops-and-heartbeat` and `projects-ui-and-patterns` specify work on
  files this audit rewrote. `check.sh` stops them breaking anything, but their
  specs may be partly obsolete and are worth re-reading before the queue
  reaches them.
